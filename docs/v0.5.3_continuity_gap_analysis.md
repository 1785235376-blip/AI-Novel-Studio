# V0.5.3 Continuity Foundation Gap Analysis

## Scope

This is an analysis-only baseline. It does not change Canon, Memory, Character,
Timeline, Chapter Accept, Lore Approval, or Agent permissions.

## Current Baseline

- `ContextIntentAnalyzer` resolves exact character/location `id` or `name` matches.
- `detect_conflicts()` reports only explicit character-state contradictions found
  by conservative text markers.
- `ContextValidationReport` is advisory and carries severity, type, description,
  and evidence IDs.
- `ContextSnapshot` already preserves the reproducible context payload and
  version markers.
- `story_state.json` currently contains chapter, story time, active characters,
  relationships, and current location, but these fields have no typed continuity
  validation contract.

## Gaps

### Timeline

There is no normalized event interval, ordering relation, reveal boundary, or
time arithmetic. The next rule layer needs deterministic checks for events that
cannot coexist at a chapter, events revealed too early, and impossible ordering.
The report must identify both event IDs and the chapter/version evidence used.

### Relationship

Relationships are currently context data, not validated state transitions. No
directed pair identity, effective chapter, transition history, or contradiction
rule exists. Validation should compare the active relationship state with
approved prior states and report incompatible simultaneous states without
mutating either source.

### Location

Only a current location string is available. There is no character location
history, travel event, scene membership, or transition timing. V0.5.3 should
start with explicit location assertions and known transitions; inferred travel
or geography should remain advisory and low confidence.

### Canon Rule Dependency

Canon is currently consumed as source material, not as a dependency graph. There
is no rule ID, prerequisite, scope, or violation severity contract. The first
increment should validate explicit rules and preserve their source/evidence IDs;
it must never promote a report to Canon.

### Character Knowledge Boundary

The current context selects active characters but does not track who knows a
fact, when it was learned, or whether knowledge is viewpoint-limited. A typed
knowledge assertion needs subject, fact/evidence ID, acquisition chapter, and
visibility scope. Unknown knowledge should be reported, not removed silently.

### Severity and Traceability

`severity` is an unconstrained string and conflicts do not distinguish hard
contradictions from warnings. Define a stable severity enum and deterministic
deduplication key. Every conflict should trace to source IDs, chapter/version,
rule ID (when applicable), and detector version.

## Proposed Boundary

Implement read-only validators behind the existing Context assembly path. Keep
the existing report shape backward compatible by extending optional fields.
Run validation after retrieval and before snapshot persistence. Apply token
budgeting before validation only if the validator explicitly records omitted
inputs; otherwise validate the complete candidate set.

Do not add LLM classification, aliases, vector search, automatic planning,
proposal approval, Canon mutation, or standalone public APIs in this phase.

## Required Test Matrix

- timeline ordering, reveal-boundary, and same-chapter contradictions;
- relationship pair/state transition conflicts;
- explicit location mismatch and unknown-location warning;
- Canon rule prerequisite and scope violations;
- character knowledge-before-reveal and viewpoint visibility;
- severity, stable conflict IDs, evidence traceability, and non-mutation;
- File/PostgreSQL parity and snapshot hash reproducibility;
- legacy `ENABLE_LORE_CONTEXT=false` compatibility.

## Exit Criteria

V0.5.3 is ready for implementation only after typed input contracts, rule
precedence, severity semantics, and persistence/versioning decisions are
explicitly approved.
