## Implemented scope

### Typed Lore schemas

Added Pydantic models for:

- Evidence
- Lore Proposal
- Proposal/Evidence Relation

The models provide JSON serialization/deserialization, enum validation, conditional source validation, review-state validation, confidence bounds, SHA-256 hash format validation, and an explicit schema version gate. Only schema version 1 is accepted; unknown versions fail explicitly.

### State machines

- Proposal: only `PENDING -> APPROVED` and `PENDING -> REJECTED`.
- Evidence: only `ACTIVE -> INVALIDATED`.
- Approved and rejected proposals are terminal.
- Evidence source content cannot be overwritten through create; duplicate IDs fail.
- Invalidated Evidence remains stored with its reason.

### File backend

`FileLoreRepository` stores one object per JSON file under:

```text
novel_data/novels/{novel_id}/lore/
  evidence/
  proposals/
  relations/
```

It uses the existing `atomic_write()` implementation and does not modify Character, Location, Timeline, Canon, Secret, Chapter, or other V0.4.8 files.

### PostgreSQL backend

`PostgresLoreRepository` implements the future Evidence, Proposal, Relation, invalidation, approval, and rejection operations using repository-local SQLAlchemy transactions and `SELECT ... FOR UPDATE` for terminal state changes.

It does not create or alter tables. Every operation first checks for:

- `evidence_records`
- `lore_proposals`
- `lore_proposal_evidence`

If they are absent, it raises a clear `Lore PostgreSQL schema is unavailable` error. Existing PostgreSQL repository composition is unchanged, so V0.4.8 runtime behavior is unaffected.

### Lore Service

`LoreService` provides:

- Evidence creation and invalidation.
- Proposal creation with Evidence relations.
- Approval and rejection.
- Mandatory Evidence and PRIMARY relation enforcement.
- Novel isolation checks.
- ACTIVE Evidence checks immediately before approval.
- Reviewer validation.

Approval currently changes Proposal state only. Character Memory creation is intentionally deferred to the next phase.

## Known limitations

- No Migration 004 exists, by requirement.
- PostgreSQL Lore operations cannot be runtime verified until a disposable database contains the future schema.
- Lore repositories are not added to `RepositoryBundle` or Factory in this phase.
- No API exposes Lore data.
- No Character Memory or Memory Snapshot is implemented.
- No Memory Agent is connected.
- No Context Pack change exists.
- File approval uses atomic replacement but does not yet provide a multi-file transaction journal; relations are validated before Proposal creation to minimize partial writes.
