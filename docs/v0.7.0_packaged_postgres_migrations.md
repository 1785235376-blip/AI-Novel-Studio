# V0.7.0 Packaged PostgreSQL Migrations

Packaged startup owns upgrades for the private PostgreSQL instance. The backend is
not started until `app/packaging/postgres_migrations.py` reports schema readiness.

## Ledger and ordering

The runner creates and uses `public.schema_migrations` with the columns
`migration_id`, `applied_at`, and `checksum`. The ordered registry is deterministic:

1. `0000_packaged_v070_baseline` adopts an existing approved legacy schema after
   checking required tables, critical columns, and foreign-key delete rules.
2. `0001_chapter_archive_state` applies
   `database/migrations/017_chapter_archive_state.sql`.

Migration SQL is hashed with SHA-256. A recorded checksum mismatch, missing
predecessor, incomplete baseline, or partially applied archive column fails closed.
Each migration and its ledger insert run in one transaction. PostgreSQL
`pg_advisory_xact_lock` serializes concurrent packaged starters.

## Startup and failure behavior

`app/packaging/packaged_processes.py` waits for PostgreSQL, runs the migration
runner, then allows backend startup. Failure stops startup and preserves the
database; no database recreation or deletion is attempted. Safe lifecycle messages
are written to the profile migration log without connection strings or credentials.

Fresh packaged databases skip the archive DDL in the generic initialization list;
the ordered packaged runner is the single owner of that change. Repeated starts
verify the ledger and schema and do not create duplicate ledger rows.

This infrastructure intentionally does not implement archive/restore APIs, UI, or
authorization behavior. Those are the next lifecycle slice after migration gates
pass.

## Chapter lifecycle contract

`chapters.is_archived` is the sole lifecycle state: `false` is ACTIVE and `true` is
ARCHIVED. Both repositories expose ACTIVE chapters through the ordinary list and
provide a separate archived list. Archive and restore preserve the chapter ID and
physical content; the file repository stores backward-compatible state in its
authoritative `chapter_state.json` metadata map. PostgreSQL uses the migrated
column. Repeated operations are idempotent, and expected-version checks reject
stale mutations. Permanent chapter deletion is outside the V0.7 lifecycle contract.
