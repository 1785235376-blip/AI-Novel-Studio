# V0.5.4 Phase 3B Context Policy and Precedence Foundation

Date: 2026-08-09

## Decision and scope

`V0.5.4 Phase 3B: PASS`

Phase 3B adds runtime-only authority metadata, deterministic precedence, exact duplicate handling, explicit structured conflict guards, cross-source budget arbitration, stable serialization, and a concise Writer consumption contract. Phase 1 through Phase 3A remain frozen. No rule, migration, source mutation, LLM arbitration, vector search, or UI was added.

## Existing architecture audit

The current Writer pack exposes accepted/current story state, approved active LoreMemoryView, and optional NarrativeContextView. Although repository context sources contain Canon and Timeline data, the existing `build_context_from_sources` contract does not expose them as independent Writer sections. Phase 3B therefore defines their policy mappings for typed callers without silently expanding the old Writer payload.

Policy runs only when Lore or Narrative Context is enabled. With both flags disabled, no policy object or contract is built and the old pack remains exactly compatible.

## Authority and source metadata

`ContextAuthorityLevel` has four stable values: `AUTHORITATIVE`, `CONSTRAINING`, `SUPPORTING`, and `ADVISORY`. Authority is independent from selection relevance and cloud locality.

The audited fixed mapping is:

```text
CANON, ACCEPTED_CHAPTER                  AUTHORITATIVE
TIMELINE, CHARACTER_KNOWLEDGE            CONSTRAINING
LORE_MEMORY, NARRATIVE_STATE,
EVIDENCE_REFERENCE                       SUPPORTING
NARRATIVE_FINDING                        ADVISORY
```

Narrative Findings cannot be promoted above ADVISORY. ContextSourceMetadata wraps source type, authority, source ID, project, ChapterVersion, Evidence IDs, stable selection reasons, locality, and optional structured fact key. It does not modify or persist Domain entities.

## Deterministic precedence and duplicates

Items sort by authority, explicit source-class order, ChapterVersion identity, stable source ID, and canonical structured value. Repository or insertion order is never used as precedence.

Exact duplicates require the same source type, source ID, ChapterVersion, and canonical value. They collapse to one item and merge reasons in sorted order. Same source identity with different values is not silently deduplicated; it enters the explicit conflict path. Natural-language similarity is not used.

## Conflict guard

Conflict detection only runs for items sharing an explicit `fact_key` and different canonical values. Different structured keys never conflict.

When one highest authority value exists, lower-authority conflicting items are omitted and a visible `HIGHER_AUTHORITY_WINS` marker records both sides. Advisory findings cannot override authoritative facts. When multiple highest-authority values conflict, all remain visible with `UNRESOLVED_HIGH_AUTHORITY_CONFLICT` and the fixed instruction not to invent a resolution. No source data, Finding, or Continuity record is changed.

`ContextConflict` is a build-time projection, not a ContinuityFinding or persisted entity.

## Writer consumption and serialization

When at least one context feature is enabled, Writer receives a short fixed contract:

```text
Higher-authority context overrides lower-authority context.
Advisories are warnings, not facts.
Do not guess through unresolved authoritative conflicts.
Context does not permit source-state mutation.
```

Serialization sections are fixed as `authoritative`, `constraining`, `supporting`, `advisory`, then `conflicts` and diagnostics. Existing within-source Narrative and Lore ordering remains intact. AgentRunner strips Lore, Narrative, and Context Policy fields from every non-Writer role.

## Budget arbitration

`CONTEXT_POLICY_TOKEN_BUDGET` defaults to 2400 deterministic estimated tokens. Allocation is independent of build call order:

```text
AUTHORITATIVE  40%
CONSTRAINING   25%
SUPPORTING     25%
ADVISORY       10%
```

Each section performs stable within-source truncation. Advisory items cannot consume authoritative capacity. Unused capacity is intentionally not reassigned in Phase 3B, keeping arbitration predictable. If authoritative data exceeds its cap, omitted source IDs are recorded and `authoritative_context_truncated=true`; completeness is never implied silently.

## Locality and cloud boundary

Locality filtering occurs before precedence and budgeting. Even an AUTHORITATIVE item marked `LOCAL_ONLY` is excluded from cloud output. Authority never changes cloud eligibility. Existing Lore cloud/privacy filtering remains unchanged; policy does not recreate or bypass it.

## Migration, limitations, and remaining work

Migration is `NOT REQUIRED`: policy metadata, conflicts, diagnostics, and budget decisions are runtime read-only projections and are not cached or persisted.

Conflict detection requires shared structured fact keys; it deliberately does not infer semantic conflicts from prose. Budget estimates remain deterministic character-based estimates rather than provider tokenizer output. Remaining work belongs only to a future explicitly requested phase. This implementation stops at Phase 3B.
