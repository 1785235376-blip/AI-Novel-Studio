# V0.5.5 Phase 2 Collaboration Scope Foundation

## Final Decision

PASS

## Scope and Frozen Baselines

V0.5.4 and V0.5.5 Phase 1 remain frozen. Narrative Rules remain 4 and Continuity Rules remain 8. Phase 1 Proposal atomicity, persistence parity, API parity, and Migration 011 remain verified.

## Collaboration Architecture

The durable hierarchy is `Workspace -> existing Project -> Storyline -> Branch`. `CollaborationScope` validates all four ownership boundaries before a scoped repository is exposed. Workspace contains no user, member, role, or permission fields.

`RevisionRef` and `ContextSnapshotRef` are typed reservations only. No revision history, merge behavior, snapshot persistence, restore behavior, or UI was added.

## Default and Legacy Scope

Legacy project access resolves deterministically to:

- Workspace: `default-workspace`
- Storyline: `default-storyline:{project_id}`
- Branch: `main:default-storyline:{project_id}`

Default creation is idempotent. Existing project APIs remain unchanged and existing File and PostgreSQL Narrative identity continues to use the legacy project partition for default/main.

## Migration and Persistence

Migration 012 creates `workspaces`, `project_workspaces`, `storylines`, and `storyline_branches`, adds `workspace_id` to `novels`, and adds typed `storyline_id` and `branch_id` columns to all nine Narrative tables. Existing projects and Narrative rows were backfilled without deleting or rewriting authoritative payloads.

Migration 012 is REAL VERIFIED on PostgreSQL. Orphan projects, storylines, and branches are zero. File metadata continues to use Windows-safe atomic writes. File/PostgreSQL repository parity and API parity are MATCH.

## Narrative and Context Scope

`ScopedNarrativeRepository` is created only after `validate_scope`. It partitions Narrative State, NarrativeEvent, Expectations, Findings, Proposals, and ChapterNarrativeLink by storyline and branch. A proposal from another branch cannot be loaded or applied. NarrativeContextBuilder receives the scoped repository view, so cross-branch and cross-storyline records are excluded before authority and relevance policy runs.

NarrativeEvent remains the only authoritative progress source and is now branch scoped. The four Narrative rules operate on an already scoped context. Finding, Proposal, and NarrativeEvent fingerprints preserve the legacy algorithm for default/main and add a scope namespace for new branches.

Canon, Timeline, CharacterKnowledge, Lore, ChapterVersion, and Evidence remain project shared. Evidence ownership continues to require the same project; branch-local narrative operations may reference project-shared evidence.

## Shared PostgreSQL Readiness

Two independently constructed PostgreSQL repository clients were verified against the same database. Workspace, Project ownership, Storyline, Branch, and same-branch NarrativeEvent were immediately visible to the second client. The second branch could not read the first branch event. No process-local coordination state is required.

## API

The minimum Workspace, Storyline, and Branch create/list endpoints are implemented. Existing `/api/projects/{project_id}/...` routes remain backward compatible and represent default storyline/main behavior.

## Explicit Non-goals

No accounts, login, permissions, RBAC, presence, WebSocket, OT, CRDT, concurrent editor, comments, merge engine, conflict resolver, collaboration UI, revision UI, snapshot persistence, or LLM proposal extraction was implemented.
