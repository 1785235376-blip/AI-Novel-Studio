## 16. Security Closure Phase 2 Re-audit

### Blocker A: Workspace Navigation Scope

- Current implementation: discovery returns workspace `id` and `name` only.
- Exact failure: frontend cannot construct a valid Project/Storyline/Branch for another workspace without guessing or retaining stale child scope.
- Files: `app/collaboration_admin.py`, `app/collaboration_admin_contracts.py`, scope repositories/services, `frontend/src/api.ts`, `WorkspaceManagement.tsx`, store integration.
- Transaction/lock boundary: read-only navigation resolution; no mutation lock required.
- Invariant: changing workspace clears all child scope and capability/member caches; an empty workspace remains empty.
- Minimal fix: backend-provided navigation context containing only validated eligible scope paths and an explicit no-default state.
- Required tests: stale Project/Storyline/Branch clearing, empty workspace, capability cache invalidation, dirty/conflict draft protection.
- Owner: Scope/Auth Closure.

### Blocker B: Workspace Create/Rename Authorization

- Current implementation: legacy create/list routes are outside the trusted collaboration admin boundary; authorized create/rename is absent.
- Exact failure: exposing the legacy services permits authorization bypass; composing create from separate calls can leave a workspace without membership/ADMIN/audit.
- Files: `app/api.py`, `app/collaboration_admin.py`, scope/identity/authorization repositories and services.
- Transaction boundary: workspace + creator membership + initial ADMIN + audit for create; workspace metadata + audit for rename.
- Lock boundary: workspace creation identity and workspace-scoped rename serialization.
- Invariant: ActorContext comes only from trusted session; DOMAIN_LEAD is not workspace ADMIN; partial creation/rename is impossible.
- Minimal fix: a repository/application atomic port for authorized create and rename; do not expose legacy mutation routes in collaboration runtime.
- Required tests: unauthorized create/rename, actor spoofing, authorized atomic success, injected audit failure rollback.
- Owner: Scope/Auth Closure with Transaction Closure port.

### Blocker C: Membership Mutation And Audit Atomicity

- Current implementation: role/permission mutation and audit share one authorization repository operation; membership mutation and audit are sequential across identity and authorization repositories.
- Exact failure: membership can commit while audit append fails.
- Files: `collaboration_admin.py`, identity/authorization repository interfaces and File/PostgreSQL implementations.
- Transaction boundary: member add/status/remove plus audit must share one commit or rollback unit.
- Lock boundary: workspace-scoped administration mutation lock for File; one PostgreSQL connection/transaction.
- Invariant: no orphan mutation and no orphan audit.
- Minimal fix: administration atomic port owning both identity and audit persistence with deterministic audit-failure injection seam.
- Required tests: forced audit failure for add/remove and representative role/permission mutations.
- Owner: Transaction Closure.

### Blocker D: File Last-admin Concurrency

- Current implementation: identity and authorization files use different locks; each operation can inspect the other file before committing its own file.
- Exact failure: concurrent member disable and ADMIN role revoke can both observe two admins and commit, leaving zero active admins.
- Files: File identity/scope repositories and a new shared workspace mutation coordinator.
- Transaction boundary: staged identity + assignment + audit changes committed together with rollback.
- Lock boundary: a shared lock keyed by workspace id across all administration-sensitive File mutations.
- Invariant: every committed state retains at least one active ADMIN.
- Minimal fix: workspace-scoped critical section covering read/check/stage/audit/commit across both files.
- Required tests: revoke/revoke, disable/revoke and duplicate grant races.
- Owner: Transaction Closure.

### Blocker E: PostgreSQL Multi-session Admin Concurrency

- Current implementation: individual paths use `FOR UPDATE`, but cross-path locking order and semantic duplicate grants are not proven with independent sessions.
- Exact failure: sequential tests cannot prove remove-versus-revoke safety, consistent lock order, or duplicate prevention.
- Files: PostgreSQL identity/scope repositories and real PostgreSQL targeted tests.
- Transaction boundary: one connection per mutation, including audit.
- Lock boundary: deterministic workspace/admin assignment/membership lock ordering.
- Invariant: at least one active ADMIN; one semantic assignment; mutation/audit parity; no unbounded deadlock retry.
- Minimal fix: align lock acquisition order and add real two-session barriers for all required variants.
- Required tests: two ADMIN revokes, disable versus revoke, concurrent duplicate grant, mutation/audit parity.
- Owner: PostgreSQL Concurrency Verification.
