# V0.5.9.1 前端人工验收指南

本指南用于在普通浏览器中验收已经封版的 V0.5.9。它启动真实 production build、FastAPI 后端、受信任会话和独立 PostgreSQL 数据库，不需要 Postman，也不需要手工编辑数据库。

## A. 启动

在 PowerShell 中进入项目目录后运行：

```powershell
cd D:\小说\AI-Novel-Studio
powershell -ExecutionPolicy Bypass -File scripts/start_acceptance.ps1
```

启动器会检查 Python、Node.js、PostgreSQL 和端口，准备非破坏性的 `ai_novel_studio_acceptance` 数据库，构建前端，等待服务健康并执行 smoke test。失败时会明确报错，不会自动杀死占用端口的未知进程。

## B. 浏览器地址

打开 <http://127.0.0.1:4173/>。后端为 <http://127.0.0.1:8000/>，PostgreSQL 为 `127.0.0.1:54329`。

## C. 进入验收身份

另开一个 PowerShell，运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/show_acceptance_identity.ps1
```

脚本显示本次启动临时生成的 ADMIN、DOMAIN_LEAD、MEMBER 会话令牌，以及四个初始 Scope 字段。把所选身份的令牌和下列 Scope 填入“连接协作项目”：

- workspaceId：`acceptance-alpha`
- projectId：`acceptance-alpha-novel`
- storylineId：`acceptance-alpha-storyline`
- branchId：`acceptance-alpha-main`

令牌由正式 trusted-session 解析器在服务端映射 Actor；前端没有 Actor 选择权。切换身份时建议使用不同浏览器 Profile，或清除该站点的 Local Storage 后重新输入令牌。不要分享令牌。

## D. 验收数据

- Workspace Alpha：包含 `Acceptance Novel Alpha`、Alpha Storyline、main Branch、带历史版本的章节。ADMIN 可管理；DOMAIN_LEAD 仅拥有 NOVEL 域管理语义；MEMBER 有 Alpha 的直接读取权限。
- Workspace Beta：包含不同的 Novel/Storyline/Branch，权限集合与 Alpha 不同，用于检查跨 Workspace 缓存刷新。
- Workspace Empty：没有 Project，用于确认 Project、Storyline、Branch 全部清空为 NONE。
- 三个用户：Acceptance Admin、Acceptance Domain Lead、Acceptance Member。

数据位于独立数据库并跨重启保留。种子可重复执行，不 drop 数据库，不覆盖同名已有记录，也不重置人工验收产生的数据。

## E. 推荐验收顺序与预期

1. 以 ADMIN 连接 Alpha。应看到真实 AppShell、ContextBar 和当前 Alpha Scope。
2. 打开工作区与团队面板。应看到 Alpha/Beta/Empty 和三名成员。
3. 创建一个带个人前缀的 Workspace，再重命名。列表应立即刷新；创建者应成为该 Workspace 的 ACTIVE ADMIN。
4. 在 Alpha 添加/停用成员，授予/撤销角色和直接权限。成功与拒绝都必须来自后端真实结果。
5. 检查 DOMAIN_LEAD：NOVEL lead 不应自动获得 IMAGE、VIDEO lead 或 Workspace ADMIN。
6. 从 Alpha 切换到 Beta。成员、角色、权限与 capability 应按 Beta 刷新，Alpha 权限不能残留。
7. 从 Alpha 或 Beta 切换到 Empty。必须显示 Workspace Empty，且 Project/Storyline/Branch 为 NONE；不得自动选取第一个子项。
8. 回到 Alpha，进入 Novel workspace，打开 `Acceptance Chapter`。正文应可见。
9. 修改正文但不要等待保存，然后尝试切换 Workspace。切换必须 fail closed，不能静默丢弃草稿。
10. 使用现有冲突/恢复入口制造安全冲突时，本地草稿和冲突记录应保留，重复冲突仍需人工处理。
11. 打开版本历史，查看 v1 详情并 Restore。Restore 应创建新 revision，历史 v1 不被覆盖。
12. 刷新浏览器并重启验收环境。已保存内容与验收数据应继续存在。

## H. 关闭

```powershell
powershell -ExecutionPolicy Bypass -File scripts/stop_acceptance.ps1
```

只停止启动器记录的 backend/frontend；只有 PostgreSQL 也是本次启动器启动时才停止该指定 data directory。不会执行 `kill all node/python/postgres`，验收数据会保留。

## I. 常见启动错误

- `PORT CONFLICT`：8000 或 4173 被未知服务占用。请自行确认并正常关闭对应程序；启动器不会强杀。
- `Node.js 20+ was not found`：安装 Node.js，或用 `ACCEPTANCE_NODE` 指定 `node.exe`。
- `.venv` 缺失：按项目依赖创建 Python 3.11+ 虚拟环境并安装项目。
- PostgreSQL unavailable：启动已配置的 PostgreSQL 16，确保 54329 可用；脚本不会下载安装基础设施。
- 页面无法连接：查看 `.runtime/acceptance-backend.stderr.log` 与 `.runtime/acceptance-frontend.stderr.log`。

## J. 确认 PostgreSQL 正常

启动末尾必须出现 `PASS PostgreSQL-backed backend health`。也可重新运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/smoke_acceptance.ps1
```
