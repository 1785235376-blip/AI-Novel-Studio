# Image creation flow: current support and gaps

This ledger follows the GitHub-derived cloud branch through the explicit-execution slice starting at `8738ecb2ecd667dd9d401c4c16c2136f812e2a17`. It describes the Rebuild image-node / original legacy image-job path. The separate `studio-image-execution/1` contract is not silently mixed into it. Existing interfaces are distinguished from verification of an actual provider run.

## Next product slice

Download reads the current readable content of the recorded asset ID. The three independent job/download/job reads do not form a transaction or pin an historical asset version. Collaboration uses the existing membership/project/branch authorization; legacy local File mode retains its original trusted-host/loopback boundary and does not gain per-actor private storage semantics from the browser association.

The next useful missing capability is an authorized read of a **pending legacy candidate**, rather than additional presentation around its raw URL. A minimal additive proposal, **not implemented here**, is a read-only original-owner candidate-content contract:

1. Resolve the existing image-job owner using the same project, actor and branch authorization as its list read; select the exact job and current execution attempt. Do not create a new candidate owner or promote a production-job schema by guessing fields.
2. Return an explicit supported/unavailable content mode and a real server observation token bound to the original row, if the existing owner can provide one. Do not name that token an output digest or formal version without such a contract.
3. Support only content already held and readable under that owner. Define byte limits, MIME, task-change/permission failure behavior and cache policy. Remote URL acquisition or ingestion requires a separate authorized design/review; no arbitrary fetch proxy or fallback to accept is proposed in this slice.
4. Let the node explicitly request that content, retire it on task/scope changes, and keep review/adoption separate. A protocol fixture can verify these rules; provider output quality and restricted media security review remain separate work.

An independently useful follow-up is server persistence of the node/task association under the existing canvas/project owner, if that owner and its versioned write contract are first identified. It must preserve current drafts and avoid creating a second graph or asset owner. External asset-query performance/pagination work and frontend shell redesign are outside this line.
