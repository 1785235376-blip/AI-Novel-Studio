# Image creation flow: current support and gaps

This ledger follows the GitHub-derived cloud branch through the explicit-execution slice starting at `8738ecb2ecd667dd9d401c4c16c2136f812e2a17`. It describes the Rebuild image-node / original legacy image-job path. The separate `studio-image-execution/1` contract is not silently mixed into it. Existing interfaces are distinguished from verification of an actual provider run.

The [explicit execution handoff](CLOUD_EXPLICIT_IMAGE_EXECUTION_20261023.md) records the current confirmation, conditional claim and unknown-outcome recovery behavior.

The October 24 [approved-image node adoption slice](CLOUD_APPROVED_IMAGE_NODE_ADOPTION_20261024.md) adds explicit viewed-content confirmation and a version/digest-bound browser-node asset association. This is separate from the original server acceptance record. The subsequent [browser history and explicit restoration slice](CLOUD_IMAGE_ADOPTION_HISTORY_20261024.md) preserves local operation history and can restore only a still-matching old pin as a new explicit local event.

The [saved-canvas contract check](CLOUD_SAVED_CANVAS_CONTRACT_BOUNDARY_20261024.md) verifies the existing display owner and strengthens its generic Save guards. Legacy-result admission remains incompatible. The later [formal image-node save slice](CLOUD_FORMAL_IMAGE_NODE_SAVE_20261024.md) implements a separate original-production t2i intent and CanvasView mapping, while keeping its unrun real reviewed-result File positive separate from queue/refusal tests and software protocol replay.

The [explicit empty-create recovery slice](CLOUD_CANVAS_CREATE_RECOVERY_20261024.md) adds a read-only original-owner lookup for new intent-bearing creates with lost acknowledgements before a Job exists. A not-found snapshot never authorizes another create; earlier intentless unknown records and lost browser hints are not silently reconstructed.

The [formal queue-request recovery slice](CLOUD_CANVAS_QUEUE_RECOVERY_20261024.md) adds durable exact request identity and a unique original-owner observation for node-bound queue admission with a lost acknowledgement. It preserves UNKNOWN after an absent snapshot, never chooses the newest matching node task and does not replay execution confirmation.

The [task-center node continuation slice](CLOUD_CANVAS_NODE_RESUME_20261024.md) reuses the existing exact task selector and original Job/Canvas/history reads to open one still-QUEUED formal node task without a browser graph or recovery hint. Its ephemeral resume-only panel preserves explicit execution confirmation and blocks new queueing, task substitution and candidate review. This is separate from the legacy browser-node path below and does not integrate the Grok unified-workspace preview.

The subsequent [read-only node-task observation slice](CLOUD_CANVAS_NODE_OBSERVE_20261024.md) opens exact RUNNING, UNKNOWN or CANCELLED original tasks through the same selector and owners. Its immutable read-only mode permits explicit same-task metadata GET and JSON receipt download; provider loading, all task operations, candidate content and review remain unavailable. Actual File evidence covers original cancellation and fresh-owner reads; other status projections do not establish real inference.

The independent [original target/save-state comparison](CLOUD_CANVAS_NODE_TARGET_OBSERVATION_20261024.md) shows an explicitly selected formal Job's captured Canvas pin alongside its current saved version, including legitimate later edits that prevent continuation. Its original-owner observation does not provision a missing File identity. It does not relax continuation, open an editor or claim that the historical request node has been restored.

The subsequent [exact saved-record view](CLOUD_CANVAS_NODE_TARGET_VIEW_20261024.md) explicitly reads that observed version's public CanvasView record through the original Job owner and displays actual saved card metadata inside the task center. It avoids the editor's local-recovery/catalog side effects. A manual reference or absent/mismatched node origin is not formal generated-node adoption; real reviewed-result save and editor restoration remain separate, unverified boundaries.

The [independent node Job metadata view](CLOUD_CANVAS_NODE_JOB_OBSERVATION_20261024.md) reads a fixed selected task without requiring the captured Canvas to remain empty or readable. It exposes only a closed metadata projection and no task actions. The original target is an unchecked request record, and candidate pins do not prove current asset/content availability. This preserves the existing continuation and save-state contracts rather than relaxing them.

The separate [explicit queued-node local discard](CLOUD_CANVAS_NODE_JOB_DISCARD_20261024.md) reuses the original cancel owner when that Canvas-dependent continuation is unavailable. Only an unexecuted QUEUED task is eligible, with fresh authority, explicit confirmation, original request binding and a complete snapshot precondition inside the original CAS. It preserves evidence and does not confirm remote cancellation. The metadata-only entry remains read-only; an uncertain write is recovered by explicit original-owner reads, never automatic resend.

The [deferred frontend regression repair](CLOUD_FRONTEND_REGRESSION_CONTRACT_REPAIR_20261024.md) returns the four previously reported 33-failure groups to their real current UI/owner contracts, preserving all 59 original scenarios. It also fixes the initial default canvas hiding an entry asset hint, without changing permissions, saved-view priority or task owners. Earlier delivery reports retain their historical unresolved counts; the new fixed-source evidence is separate from any whole-suite acceptance claim.

## Next product slice

Download reads the current readable content of the recorded asset ID. The three independent job/download/job reads do not form a transaction or pin an historical asset version. Collaboration uses the existing membership/project/branch authorization; legacy local File mode retains its original trusted-host/loopback boundary and does not gain per-actor private storage semantics from the browser association.

The next useful missing capability is an authorized read of a **pending legacy candidate**, rather than additional presentation around its raw URL. A minimal additive proposal, **not implemented here**, is a read-only original-owner candidate-content contract:

1. Resolve the existing image-job owner using the same project, actor and branch authorization as its list read; select the exact job and current execution attempt. Do not create a new candidate owner or promote a production-job schema by guessing fields.
2. Return an explicit supported/unavailable content mode and a real server observation token bound to the original row, if the existing owner can provide one. Do not name that token an output digest or formal version without such a contract.
3. Support only content already held and readable under that owner. Define byte limits, MIME, task-change/permission failure behavior and cache policy. Remote URL acquisition or ingestion requires a separate authorized design/review; no arbitrary fetch proxy or fallback to accept is proposed in this slice.
4. Let the node explicitly request that content, retire it on task/scope changes, and keep review/adoption separate. A protocol fixture can verify these rules; provider output quality and restricted media security review remain separate work.

An independently useful follow-up is server persistence of the node/task association under the existing canvas/project owner, if that owner and its versioned write contract are first identified. It must preserve current drafts and avoid creating a second graph or asset owner. External asset-query performance/pagination work and frontend shell redesign are outside this line.
