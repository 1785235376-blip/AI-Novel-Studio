## D-01 (P2, FIXED) — `pnpm test` fails because Vitest collects Playwright e2e specs

- **Symptom**: `cd frontend && corepack pnpm test` exits 1 with 3 "Failed Suites":
  `e2e/prompt-acceptance-s0.spec.ts`, `e2e/prompt-workspace-acceptance.spec.ts`,
  `e2e/studio-release-acceptance.spec.ts` — "Playwright Test did not expect test() to be called
  here". All 4,303 actual unit tests passed; the frontend gate was still red.
- **Minimal reproduction** (before fix): `cd frontend; corepack pnpm test` →
  `Test Files 3 failed | 397 passed | 2 skipped`; exit 1.
- **Root cause**: Vitest default include matches `*.spec.ts`; the Playwright specs live in
  `frontend/e2e/`, but `frontend/vite.config.ts` only excluded `tests/e2e/**` and
  `tests/visual/**`.
- **Fix**: add `'e2e/**'` to `test.exclude` in `frontend/vite.config.ts`.
- **Regression**: `cd frontend; corepack pnpm test` → `397 passed | 2 skipped`, exit 0;
  `pnpm build` and `pnpm lint` pass (evidence: frontend summary in
  `evidence/20261019-r1/`).

## D-02 (P1, FIXED) — CJK Windows: image job listing cannot read its own UTF-8 JSON

- **Symptom**: on a Chinese-locale Windows host (`cp936`), `ImageJobService.list()` raises
  `UnicodeDecodeError: 'gbk' codec can't decode ...` for any job row containing non-ASCII text
  (Chinese prompt/title). Image generation history becomes unreadable/corrupted behavior.
- **Minimal reproduction** (before fix):
  `atomic_write(path, json.dumps([{'title': '中文标题'}], ensure_ascii=False)); path.read_text()`
  → `UnicodeDecodeError: 'gbk' codec can't decode byte 0xad` (captured at
  `Engineering-Runs/20261019-r1/repro-locale-read.py`, `PREFERRED=cp936`).
- **Root cause**: `app/services/image_job_service.py::_load` used `Path.read_text()` without an
  encoding. `app.storage.atomic_write` always writes UTF-8, so the reader's implicit locale
  encoding is wrong on any non-UTF-8 locale.
- **Fix**: `path.read_text(encoding='utf-8')`.
- **Regression**: `tests/test_windows_locale_utf8_persistence.py` (UTC-8 round-trip + explicit
  encoding spy) → PASS; static guard over `app/` for missing encoding → PASS.

## D-03 (P1, FIXED) — CJK Windows: video assembly job list cannot read its own UTF-8 JSON

- **Symptom**: same failure mode as D-02 for `VideoAssemblyService.list()`:

- **Root cause**: `app/services/video_assembly_service.py::list` used `path.read_text()` without

- **Regression**: `tests/test_windows_locale_utf8_persistence.py` → PASS.

## D-04 (P2, FIXED) — Windows/CJK locale: four tests read UTF-8 fixtures with the locale codec

## D-05 (P3, FIXED) — Windows: symlink tests fail instead of skipping without the privilege

- **Symptom**: `OSError: [WinError 1314]` / "client does not have the required privilege" in
  `test_asset_lifecycle_r2`, `test_local_ai_environment_v2`, `test_r4_portable_batches` when
  creating symlinks without Developer Mode/SeCreateSymbolicLinkPrivilege.
- **Root cause**: the tests assume symlink creation is permitted; the hosted Linux CI provides it,
  the default Windows developer session does not.
- **Fix**: explicit `pytest.skip('WINDOWS_SYMLINK_PRIVILEGE_UNAVAILABLE: ...')` only for
  WinError 1314; the symlink security contracts remain covered by hosted Linux CI and are not
  removed or made optional for supported environments.
- **Regression**: the three nodes report SKIP with the explicit reason; no other assertion changed.

## D-06 (P3, FIXED) — pinned font preparation is flaky on truncated downloads

- **Symptom**: `python scripts/prepare_pdf_font.py --output <dir>` intermittently raised
  `pinned font/license integrity check failed` because the variable font download returned a
  short body (observed 17,760,384 / 17,614,208 / 17,736,448 of 17,772,300 bytes; also
  `IncompleteRead` on one attempt).
- **Root cause**: plain `urlopen` with a single attempt; no retry for transient truncation. The
  integrity check failed closed correctly (no bad font written), so this was availability, not
  corruption.
- **Fix**: send a normal User-Agent, retry up to 4 times, and keep the pinned SHA256 as the only
  authority; incomplete bodies are never written.
- **Regression**: fresh `--output` run exits 0 with the exact pinned hashes
  (`NotoSansSC-Variable.ttf` `a3041811...`, `NotoSansSC-Regular.ttf` `eeb06b8a...`,
  `OFL.txt` `1c05c68c...`); `tests/test_r2_pdf_font.py` 4 passed.

## D-07 (P2, OPEN/ENV) — PostgreSQL-mode suite hangs in the cross-process Local Interop host test

- **Symptom**: the complete PostgreSQL-mode run (both the full suite and the
  `postgres_backend_only` subset) stops making progress at
  `tests/test_local_interop_cross_process_host.py::test_real_host_api_metadata_guidance_diagnostics_verifier_and_revocation[postgres]`.
  PostgreSQL shows idle `COMMIT` sessions; no server-side query is running.
- **Evidence**: the pytest-timeout thread dump (120 s) shows the main thread inside
  `host.diagnostic_preview` → `provider.authorize` → authorization scope validation →
  `psycopg.connect` waiting in `select` (full stack retained in the round logs).
- **Second PG symptom (same class)**: later PostgreSQL shards then stalled at random tests; the
  isolated server log records repeated
  @@LOG: could not reserve shared memory region (addr=...) for child ...: error code 487@@ while
  accepting connections. Error 487 is the known Windows PostgreSQL address-space/ASLR class of
  failure that makes new backends fail to start, so the client waits in @@psycopg.connect@@. This is
  an environment problem of this host, not an application defect.
- **Current disposition**: ENV/PLATFORM — full PG-mode execution is reported PARTIAL for this host.
  Mitigation used: restart the disposable cluster with test-only settings (@@fsync=off@@,
  @@synchronous_commit=off@@, @@shared_buffers=64MB@@, @@max_connections=64@@) and run a
  representative real-PostgreSQL contract subset instead of the full 4,818-node set. The subset
  result is recorded in @@backend-pg-subset@@; the full PG suite remains BLOCKED_ENVIRONMENT until a
  clean host/runner is available. It must be reproduced on a clean Windows machine and Linux CI
  before being called a product defect; no product code was changed for it.
- **No code change** was made for D-07 in this round; the exclusion is recorded in
  `Engineering-Runs/20261019-r1/pg-shard-assignment.json` (`excluded` list).

## D-08 (P2, FIXED) — Python 3.11 rejects WAVE_FORMAT_EXTENSIBLE; 96 kHz PCM trim jobs fail

- **Symptom**: @@test_v2_audio_wav_controls.py::test_real_boundary_profiles...@@ with 96,000 Hz
  stereo PCM jobs ended @@FAILED@@ (generic @@STUDIO_AUDIO_EXECUTION_FAILED@@) instead of
  @@AWAITING_REVIEW@@. The product advertises 8,000–96,000 Hz trim profiles.
- **Minimal reproduction**: run the same ffmpeg trim command the service uses
  (@@-ss 0.100 … -ar 96000 -ac 2 -c:a pcm_s16le -f wav@@) on a 16 kHz WAV. ffmpeg exits 0 and
  writes a 268,902-byte WAV whose fmt tag is @@0xFFFE@@ (WAVE_FORMAT_EXTENSIBLE, 40-byte fmt,
  PCM subformat GUID). @@app.media_files.inspect_media@@ used Python's @@wave@@ module, which on
  Python 3.11 raises @@wave.Error: unknown format: 65534@@ for that file.
- **Root cause**: the declared minimum Python is 3.11, but the validator relied on a standard
  library that only gained extensible-PCM support in 3.12. The job wrapper hid the cause behind a
  generic error code.
- **Fix**: bounded read-only RIFF/WAVE parser in @@app/media_files.py@@ that accepts classic PCM
  (format 1) and extensible PCM subformat, rejects non-PCM/truncated/short data, and a
  @@normalize_pcm_wav@@ step that rewrites <=2-channel 16-bit extensible PCM trim output as
  classic RIFF PCM (payload preserved byte for byte) so older readers keep working. Audio
  concatenation now reads PCM payloads through the same parser.
- **Regression**: @@tests/test_media_wav_extensible_validation.py@@ (5 tests) PASS; the previously
  failing 96 kHz boundary nodes PASS; related media/comic batch **106 passed, 0 failed**
  (evidence @@backend-pg-subset@@ / @@media-family-after-fix@@).

## Round-2 triage addendum (2026-10-19, same engineering session)

Round 2 classified all 203 failed/error node ids from the round-1 complete File run.
Full classification and per-run commands are in [TRIAGE_20261019_r2.md](TRIAGE_20261019_r2.md).

### D-11 (P1, FIXED) — collaboration runtime blocked blank-project creation

- **Symptom**: with `ENABLE_COLLABORATION_RUNTIME=true`, `POST /api/experimental/projects`
  returned 501 `COLLABORATION_ROUTE_NOT_ENABLED`; the R3-I authorized/adoption flows and the
  studio blank-project entry could not create a project over HTTP.
- **Root cause**: the collaboration middleware allowlist in `app/main.py` never admitted the
  real blank-project route (`app/creative/workspace_api.py`) that the frontend and the
  R3-I suites call.
- **Fix**: added `(method == "POST" and normalized_path == "/api/experimental/projects")` to the
  collaboration allowlist. Session/authorization still gate the route itself.
- **Verification**: R3-I adoption 4/4 PASS (collaboration off), R3-I authorized 8/8 PASS
  (collaboration on); prompt-adoption revocation suite 22/24 PASS.

### D-12 (P2, FIXED) — interop contract generator emitted CRLF on Windows

- **Symptom**: `test_contract_manifest_matches_bytes_and_regeneration` failed: generated
  `handshake.schema.json` had CRLF bytes while the checked-in contract is LF.
- **Root cause**: `local_interop_protocol/generate_contracts.py` used text-mode
  `write_text` without `newline="\n"`, so Windows translated every newline and
  regenerating contracts on Windows would corrupt the parity manifest.
- **Fix**: all generated artifacts (schemas, protocol.ts, protocol.rs, parity manifest) are
  now written with `newline="\n"`; contract files and manifest were regenerated and the
  parity manifest now pins the updated generator hash.
- **Verification**: `test_local_interop_contracts.py` PASS; 208-test catalog/interop/guard batch PASS.

### D-13 (P2, FIXED) — Windows receipt reads missed same-size in-place rewrite

- **Symptom**: `test_v2_windows_timeline_receipt_identity` expected
  `STUDIO_TIMELINE_RECEIPT_INVALID` after an in-place write that preserved size and restored
  mtime/atime; Windows accepted it (DID NOT RAISE).
- **Root cause**: Windows `stat` exposes creation time as `st_ctime`, not the NTFS
  ChangeTime; the existing snapshot therefore could not observe the write.
- **Fix**: new `app/windows_file_identity.py` reads the real NTFS ChangeTime through
  `GetFileInformationByHandleEx(FileBasicInfo)` for both the path and the open descriptor;
  `VideoAssemblyService._studio_receipt_bytes` now includes it in the pre/open/post
  snapshots. Non-Windows behavior and error mapping are unchanged.
- **Verification**: receipt identity suite PASS; `test_v2_studio_receipt_bounds.py` PASS.

### D-14 (P2, FIXED) — API catalog stale against the mounted sources

- **Symptom**: `test_surface_api_catalog.py` reported 51 differing source hashes and
  missing operations; the catalog had not been refreshed after later branch commits.
- **Fix**: `scripts/refresh_product_api_catalog.py` refreshed the catalog to 2269 mounted
  operations (26 added, 0 removed) and rebound every `app/**/*.py` source hash, including the new
  `app/windows_file_identity.py`. Catalog tests PASS.

### D-15 (P2, FIXED in test, no product change) — legacy project scope contract drift

- **Symptom**: `test_v060_project_path_persistence` created storylines/branches for a legacy
  linked project whose novel metadata is gone; the product now fails these writes closed
  (`ValueError: project does not exist`) after the documented security hardening commit
  `62d4aaf6` ("close legacy project authority and scope races").
- **Resolution**: the test now models the real migration state (scope rows created through the
  repository, as an old install would have them), keeps the navigation-tolerance assertion
  (`未命名小说`) and adds an explicit fail-closed write assertion. Product behavior unchanged.

### D-16 (P3, FIXED in tests) — stubs outdated against current persistence contracts

- `test_collaboration_http_boundary_v056` stubbed `novel_service` without its
  `novels` repository, while collaboration-mode deletion now runs through
  `AtomicPathMutationPort`. The stub now supplies the repository and keeps the
  authorized-delete intent.
- `test_a43_file_identity` stubbed authorization without the `mutation()` context
  manager now used by `FileAtomicChapterAuditPort`; the stub now supplies it.

### D-17 (P3, OPEN / HARNESS) — prompt-process revocation is timing-sensitive on Windows

- Observed on the full 48-case run: 22 passed, 2 failed, 24 skipped (postgres-marked).
  The two failures (writer-permission-delete-file, writer-permission-adopt-file) both
  surfaced a child worker JSON decode error under load; isolated reruns gave 4/4 pass and
  then 3/4 (the same intermittent case). Classified HARNESS/INTERMITTENT, not claimed PASS.

### D-18 (P3, OPEN / WINDOWS) — R4 performance worker network guard on Windows

- `test_flags_off_worker_uses_real_mounted_file_api_and_no_network` fails on Windows because
  the benchmark records `blocked_connect_attempts=1` and therefore raises
  `RuntimeError('benchmark forbids all network connections')` (status ERROR,
  `partial_measurements_retained=true`). This is the benchmark failing closed, not a fake
  measurement; the clean-run contract is exercised by hosted Linux CI.

  `test_v2_adaptation_asset_owner.py`, `test_local_interop_contracts.py`,

  ids (Windows environment-variable limit), and the hostile backslash archive case is skipped on
