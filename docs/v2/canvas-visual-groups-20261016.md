## Implemented workflow and ownership

GraphCanvas now mounts a functional visual-group panel: explicitly select nodes, enter a name and create a group; choose an existing group to rename it, select all members, or remove only its grouping. The member list is readable independently of viewport culling. Selecting members feeds the existing canvas selection, which retains selected cards even outside the viewport; dragging any selected member moves the selection with the existing world-coordinate, zoom, snapping and boundary behavior. Group metadata itself has no duplicate positions or synthetic execution nodes. Spatial group outlines are not implemented in this slice.

`presentation.groups` is optional in the original Graph definition, alongside the existing optional `presentation.comment`. Each group has an ID (existing ASCII ID contract), a strict nonblank name of at most 80 Unicode code points, and 1–24 unique existing node IDs. There are at most 24 groups. Membership is disjoint: a node can belong to only one group, and overlapping groups are rejected rather than silently reassigned. IDs are unique within groups; names need not be unique. The panel states these constraints and shows the exact members. Remove the original group before regrouping its members. Schema versions 1–5 accept the same additive presentation contract without changing their execution node catalogs or 16/24/40 budgets.

Absent presentation and absent nested fields stay omitted during serialization. Existing comment-only records retain their exact canonical values/digests; empty/whitespace annotation text is preserved. Empty group arrays and explicit null nested fields are rejected. Removing the last group omits groups and, when no comment remains, presentation. Annotation edit/removal preserves groups. Group removal never deletes nodes/edges/assets. Both original UI node-removal paths now use `removeGraphNodes`, which prunes memberships, removes empty groups, and preserves protected nodes and comments in the same history change. Malformed/dangling server requests are rejected by the original Graph schema, not repaired into another meaning.

Original draft history, dirty detection, undo/redo, explicit Save, version/CAS and reopen remain the only persistence owner. No new store/API/queue/permission mechanism exists. The pending name input is transient and resets on definition/owner/blocked transitions. Readonly/busy/gesture states disable group controls, and control keyboard events are isolated. UNKNOWN/conflict saves preserve the group draft and disable writes until original explicit reconciliation. Execution projection, source pins, budgets, review and authority are unchanged. Existing CanvasOps session-only experiments remain distinct and are not promoted to persistence by this feature.
