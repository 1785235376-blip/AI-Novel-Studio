## Migration

Added `database/migrations/005_lore_memory.sql`. It only creates `character_memories`, `memory_snapshots`, their constraints/indexes, and the `0.5.1-memory` schema marker. Migrations 001–004 were not modified.

Character Memory enforces stable business IDs, approved Proposal linkage, valid status/type domains, range ordering, supersession links, and retraction reasons. Snapshot enforces scope, version uniqueness, range ordering, watermark/content fields, and supersession links.

No existing Character, Canon, Timeline, Secret, or Chapter ORM was changed.

## Repository

Both File and PostgreSQL Lore repositories now support:

- create/get/list Character Memory;
- list all novel memories by status;
- supersede and retract Memory;
- atomic Proposal approval with Memory creation;
- create/list/latest Memory Snapshot.

PostgreSQL uses one transaction and a locked Proposal row. Evidence is revalidated inside the transaction. If Character or Memory creation fails, the transaction rolls back and Proposal remains PENDING. File mode restores the original Proposal and removes the new Memory on failure.

External Memory/Snapshot/Proposal IDs and Character slugs are restored at the serialization boundary; internal UUIDs are not returned.

## Memory Service

Added `app/services/memory_service.py`.

- Only `CHARACTER_MEMORY` PENDING Proposals can use the Character Memory approval path.
- Approved payload, reviewer, Evidence status, and novel isolation are validated.
- Agent code cannot directly participate; no Agent is connected.
- Snapshot generation reads only ACTIVE Memory.
- Snapshot payload is canonicalized before SHA-256 calculation.
- Watermark records Memory IDs and update times.
- Version increments per novel/scope/scope key and links the prior Snapshot.
