# V0.5.4 Phase 2B Structured Narrative Progress Foundation

Date: 2026-08-09

## Decision

`V0.5.4 Phase 2B: PASS`

## Scope and frozen baselines

Phase 2B adds explicit Mystery, CharacterGoal, and ChapterNarrativeLink state. Phase 1 state and Phase 2A expectation/finding semantics remain unchanged. Narrative rules remain exactly `FORESHADOWING_OVERDUE` and `THREAD_STALE`; no inference, LLM, Writer Context, UI, or new finding rule was added.

## Domains and lifecycle

Mystery supports `OPEN -> DEVELOPING/ANSWERED/ABANDONED` and `DEVELOPING -> ANSWERED/ABANDONED`. CharacterGoal supports `ACTIVE <-> SUSPENDED` and transition from either active state to `COMPLETED/FAILED/ABANDONED`. Terminal states reject reopening.

Both entities are explicit, project-scoped records. CharacterGoal creation verifies the character belongs to the same project.

## Explicit chapter narrative mapping

`ChapterNarrativeLink` contains a project, current chapter ID and version, typed entity/action, summary, evidence IDs, and event ID. Supported entities are `PLOT_THREAD`, `FORESHADOWING`, `MYSTERY`, and `CHARACTER_GOAL`; action compatibility is enforced by a typed matrix.

Narrative Progress Source of Truth: `NarrativeEvent` is authoritative. A ChapterNarrativeLink is its structured projection. `NarrativeStateService.record_chapter_narrative_progress()` validates provenance and domain lifecycle, creates the event, projects the link, and changes the entity in one repository transaction. A link cannot independently mutate state.

## Provenance policy

Only the current accepted Chapter version may drive authoritative narrative progress. The service compares `chapter_id`, project ownership, and exact current version. Every non-empty Evidence ID is resolved through Lore persistence and must belong to the same project. Empty evidence remains legal and no synthetic Evidence is created.

Real API parity included a non-empty PostgreSQL Lore Evidence record and preserved the Evidence ID on File and PostgreSQL Narrative backends. The environment was missing frozen Lore tables; unmodified Migrations 004 and 005 were executed to restore that baseline before verification.

## Persistence and migration

Migration 010 creates typed `narrative_mysteries`, `narrative_character_goals`, and `narrative_chapter_links` tables. It was executed against PostgreSQL 16 and verified through `information_schema`. Migrations 008 and 009 were not modified.

File persistence uses the existing Windows-safe `atomic_write`. PostgreSQL persistence uses one connection transaction with an entity row lock. Repository Factory continues routing the narrative dependency to File or PostgreSQL implementations.

## Atomicity and rollback

A real PostgreSQL unique-key failure was forced after the entity update statement but before event/link completion. The transaction rolled back: the Mystery remained `OPEN` and the link was absent. File failure injection caused `atomic_write` to raise while the previous file state remained byte-semantically unchanged.

## API

The API provides project-scoped create/list/detail/transition endpoints for Mysteries and Character Goals, a single create/list Chapter Progress API, and extends the existing Narrative State response with `mysteries` and `character_goals`. Illegal transitions return 400; cross-project entity access returns 404.

## Known limitations and remaining work

The foundation accepts explicit structured commands only. It does not infer mysteries, goals, mappings, progress, answers, or payoffs. It does not expose these records to Writer Context. Future V0.5.4 phases are the only remaining work; this implementation stops at Phase 2B.
