## 4. Identity Runtime

- `User`: persistent File/PostgreSQL identity
- `WorkspaceMembership`: active membership gate, separate from permissions
- `SessionContext`: session, client, actor, workspace and correlation identity
- `ActorContext`: immutable binding to its trusted SessionContext
- HTTP clients submit an opaque session token; actor IDs from request payloads are not trusted
- Local bootstrap is available through server-owned `COLLABORATION_DEV_SESSIONS_JSON`; the resolver remains replaceable by a future authentication provider

## 5. Authorization Runtime

- Existing `DomainRoleAssignment` and `PermissionAssignment` remain authoritative
- Membership answers whether an actor belongs to a workspace
- Domain permissions answer what that member may do
- ADMIN and DOMAIN_LEAD compatibility is preserved
- Collaboration-aware chapter reads/writes require an explicit branch scope
- Unintegrated API routes fail closed while collaboration mode is enabled

## 6. Optimistic Concurrency

- Chapter writes use `expected_version`
- PostgreSQL uses one conditional `UPDATE ... WHERE version = expected_version`
- One winner increments the version; stale writers receive structured HTTP 409
- File mode provides the same logical conflict contract with same-process serialization
- Autosave uses its durable local version and preserves dirty state after conflict
- Generation jobs persist `base_chapter_version`; AI_ACCEPT must use that generation base and cannot silently adopt a newer chapter version

## 7. Multi-client Verification

- Same user, two clients, same chapter: stale client conflicts
- Different users, two clients, same chapter: exactly one winner
- Independent ActorContexts and sessions remain distinct
- PostgreSQL race uses separate repository/service instances and database sessions
- Unauthorized or inactive members cannot mutate the chapter
- A caller cannot inspect or accept another actor's generation job in collaboration mode
- File updates to different chapters preserve every event in the shared audit file

## 8. Revision

- Existing chapter history is the immutable revision foundation
- Meaningful reasons: `MANUAL_SAVE`, `AI_ACCEPT`, `RESTORE`, `CHAPTER_SWITCH`, `EXPLICIT_CHECKPOINT`
- Debounced autosave persists content without creating a permanent revision on every keystroke
- Restore creates a new current version and does not modify historical rows
- PostgreSQL history now returns reason, actor, session, scope and metadata consistently

## 9. ContextSnapshot

- Context Pack v1 and v2 are preserved
- Canonical hashing is deterministic
- Snapshot persistence occurs before provider streaming when collaboration runtime requires it
- Snapshot failure prevents model invocation
- Every generation stores a durable `generation_jobs.context_snapshot_id`
- Retry of the same generation is idempotent
- Different generations with identical context receive distinct snapshots and retain correct provenance
- LOCAL_ONLY cloud checks remain fail-closed

## 10. Audit

- Success audit records actor, action, scope, target and version identifiers
- Sensitive chapter content, prompts and secrets are excluded from audit metadata
- PostgreSQL chapter CAS, revision and success audit commit in one transaction
- File mode holds a global authorization-file lock across chapter save, audit append and compensation
- Conflict audit is content-free and best-effort without masking the authoritative conflict
