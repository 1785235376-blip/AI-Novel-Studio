## Existing Optimistic Locking Audit

The existing Chapter `version` and `VersionConflict` contract protects an individual chapter document. It is retained unchanged. BranchRevision is a separate branch-wide collaboration sequence and does not replace ChapterVersion, NarrativeEvent identity, or Proposal identity.

## BranchRevision Domain and Source of Truth

`BranchRevision` contains workspace, project, storyline, branch, and a non-negative monotonic integer revision. The single durable source of truth is `storyline_branches.revision`. Initial revision is 0. No duplicate branch revision table exists.

Migration 013 adds `revision BIGINT NOT NULL DEFAULT 0 CHECK(revision >= 0)`. It was applied to the real PostgreSQL database. All existing branches were backfilled; NULL revisions and negative revisions are both zero.

## Tracking and Enforcement

Revision coverage is `AUTHORITATIVE_MUTATION_REVISION`:

- Narrative entity lifecycle transitions bump revision.
- Chapter Narrative progress, NarrativeEvent, and ChapterNarrativeLink commits bump revision.
- Proposal accept and its authoritative apply bump revision.
- Duplicate Proposal accept is idempotent and does not bump twice.
- Proposal create/reject, Expectation writes, and Finding reconciliation do not currently bump revision.

Tracking is active on revision-aware and resolvable legacy default-scope authoritative writes. Enforcement is controlled by `ENABLE_OPTIMISTIC_CONCURRENCY`, which defaults to false. Scope-aware mutation APIs always require `expected_revision`. Legacy APIs remain compatible while enforcement is disabled.

## Scope Before Revision

The order is scope validation, revision validation, domain validation, and mutation. A scope mismatch is rejected before branch revision is returned, preventing cross-scope revision disclosure.

## PostgreSQL CAS and Atomicity

PostgreSQL uses `UPDATE storyline_branches SET revision = revision + 1 WHERE id = ? AND revision = ? RETURNING revision`. CAS and Narrative business SQL execute on the same connection and transaction. Forced event insertion failure rolled back the entity mutation, link insertion, and revision increment together.

Two independent PostgreSQL clients were verified. Both read revision 0. Client A committed revision 1. Client B's stale revision 0 write was rejected without mutation. After refresh, Client B committed revision 2. A different branch remained at revision 0.

## File Semantics

File uses read/compare, Windows-safe atomic replacement, and compensating restoration of the Narrative snapshot if revision persistence fails. It provides local, same-process semantic parity. Multi-machine collaboration is supported only by PostgreSQL; ordinary shared File storage is not a cross-machine CAS backend.

## RevisionConflict and API

`RevisionConflict` carries expected revision, current revision, and complete scope. APIs map it to HTTP 409 with `STALE_REVISION`, `expected_revision`, and `current_revision`. Missing expected revision on enforced writes is rejected. Successful scope-aware writes return the new current revision.

File and PostgreSQL API parity is MATCH for missing revision, successful writes, stale writes, conflict responses, refresh, and branch isolation.

## Proposal Integration

Proposal accept retains scope ownership, status, ChapterVersion, evidence, and lifecycle revalidation. A successful accept atomically commits Proposal ACCEPTED, entity mutation, NarrativeEvent, ChapterNarrativeLink, and revision increment. Stale or failed accept leaves Proposal, Narrative state, and revision unchanged. Duplicate accept remains idempotent.

## Context and Fingerprints

`ContextSnapshotRef` now binds a `BranchRevision` as provenance. Reading context or constructing the reference does not increment revision and does not change ContextPolicy authority or relevance.

Revision is excluded from Finding, Proposal, and NarrativeEvent semantic fingerprints. Legacy default/main Finding and Proposal identities remain stable.
